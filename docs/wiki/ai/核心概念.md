## 1. 大模型（LLM，Large Language Model）

### 是什么
- 基于**Transformer**架构（2017 年提出），通过海量文本**预训练**学到的语言模型。
- 核心能力：**预测下一个 token**（next-token prediction）。对话、写作、代码、推理等能力都是"预测下一个词"这一目标在超大参数量 + 海量数据下涌现出来的。
- 代表：GPT 系列、Claude 系列、豆包（Doubao）、DeepSeek、Qwen、LLaMA 等。

### 关键技术点（面试常问）
- **Transformer**：自注意力机制（Self-Attention）、多头注意力（Multi-Head Attention）、位置编码（Positional Encoding）。
- **预训练 → 微调 → 对齐** 三阶段：
  - 预训练（Pre-training）：学习通用语言能力。
  - SFT（监督微调）：用人工标注的问答对教它"听指令"。
  - RLHF / DPO（对齐）：让输出符合人类偏好、更安全。
- **涌现能力（Emergent Abilities）**：参数量/数据量到一定规模后出现的能力，如推理、少样本学习（few-shot）。
- **参数量、训练数据、上下文长度**是衡量模型规模的主要维度。

### 常见问题
- Q：大模型会"思考"吗？
  A：不会。它只是根据概率生成最可能的词序列，没有真正的心智，输出可能"一本正经地胡说"（幻觉，Hallucination）。
- Q：为什么需要 RAG？
  A：模型知识有截止日期、会幻觉，RAG（检索增强生成）从外部知识库检索真实信息喂给模型，减少幻觉、保证时效。

## 2. Token

### 是什么
- 模型处理和生成文本的**最小单位**。可以是一个单词的一部分、一个完整的词、一个标点或一个汉字片段。
- 中文通常 **1 个汉字 ≈ 1~2 个 token**；英文 **1 个词 ≈ 1~1.5 个 token**（因分词规则而异）。

### 为什么重要
- **计费单位**：API 按输入+输出 token 数收费。
- **上下文上限单位**：模型的上下文长度以 token 计。
- **性能**：token 越多，生成越慢、成本越高。

### 常见问题
- Q：token 和字符的区别？
  A：token 是分词器（Tokenizer）切出来的单位，字符是文本字面单位；1 个 token 可能对应多个字符或半个汉字。
- Q：如何估算 token 数？
  A：中文约 1 汉字 ≈ 1~2 token；可用各家 tokenizer 工具精确计算；模型上下文上限通常也是 token 数（如 128K、256K）。
- Q：为什么"同样的文字 token 数不同"？
  A：取决于分词器（BPE / SentencePiece 等）和语言的切分粒度。

## 3. Context（上下文）

### 是什么
- 模型在一次请求中**能看到的所有信息**的总和：系统提示词（System Prompt）+ 用户输入 + 历史对话 + 工具返回的结果等。
- 也就是每次调用时拼装后喂给模型的全部 token。

### 两个层面
- **上下文窗口（Context Window）**：模型单次能容纳的最大 token 数（如 128K、256K、1M）。
- **上下文管理**：在多轮对话 / Agent 中如何组织、取舍、压缩、检索历史信息。

### 为什么重要
- 超出窗口会被截断（可能丢失关键信息）→ 需要**压缩、摘要、滑动窗口、RAG 检索**等策略。
- 上下文越长：成本越高、生成越慢、注意力衰减（"lost in the middle"，中间信息容易被忽略）。
- 上下文 = 模型的"短期工作记忆"，**不持久**，下次请求默认遗忘。

### 常见问题
- Q：模型有长期记忆吗？
  A：默认没有。跨会话记忆需要外部存储（如向量数据库 + 检索，或专门记忆模块）。
- Q：上下文窗口越大越好吗？
  A：越大能承载更多信息，但成本和延迟上升、长文本处理质量可能下降，需要权衡。
- Q：如何让模型"记住"之前聊过的内容？
  A：把历史对话拼进 context，或用记忆系统/外部数据库在需要时检索回填。

## 4. Prompt（提示词）

### 是什么
- 用户向模型输入的自然语言指令/内容，用于引导模型产出期望结果。
- 包括：系统提示（System）、用户提示（User）、助手历史（Assistant）等角色。

### 关键技巧（Prompt Engineering）
- **角色设定**："你是一位资深后端工程师"。
- **明确指令**：说清目标、格式、约束（"分点列出""用表格""不超过 200 字"）。
- **Few-shot（少样本）**：给几个示例，让模型模仿。
- **结构化**：用分隔符、步骤编号、输出格式说明（JSON 等）。
- **CoT（思维链）**："请一步步思考"，提升复杂推理。
- **迭代优化**：根据输出不断修正。

### 与 System Prompt 的区别
- System Prompt：设定模型的"人设、规则、边界"，优先级高，一般由应用方控制（如安全规则）。
- User Prompt：用户的具体请求。

### 常见问题
- Q：Prompt 会决定什么？
  A：影响输出的质量、格式、风格、是否合规，但不改变模型的知识和能力上限。
- Q：Prompt 注入（Prompt Injection）是什么？
  A：攻击者把恶意指令藏在输入/网页内容里，诱导模型执行非预期操作（如泄露 prompt、越权调用工具）。需要做输入校验、权限隔离。

## 5. Tool（工具调用 / Function Calling）

### 是什么
- 让模型**调用外部函数/API**来完成任务的能力：模型不直接执行代码，而是"声明要调用哪个工具、传什么参数"，由应用层真正执行并把结果返回给模型。
- 本质：把模型的"语言能力"扩展为"行动能力"。

### 工作流程
1. 定义工具（函数名、描述、参数 schema）。
2. 模型根据任务决定是否调用某工具并生成参数（JSON）。
3. 应用层执行工具、拿到结果。
4. 把结果作为新上下文回传给模型，模型继续推理直到完成任务。

### 工具的类型
- 查询类：搜索、查数据库、读文件、天气、行情。
- 执行类：发邮件、写代码、操作网页、调用内部系统。
- 计算类：精确计算（规避模型算术弱点）。
- 记忆类：读写向量库、KV 存储。

### 为什么需要工具
- 补足模型的**短板**：实时信息、精确计算、访问私有数据、执行实际动作。
- 是 Agent 的核心能力之一。

### 常见问题
- Q：Function Calling 和普通调用 API 的区别？
  A：Function Calling 让模型**自主决定**何时、用什么参数调用，而不是应用预先固定好调用逻辑。
- Q：工具结果如何处理？
  A：作为上下文回填给模型，供其继续推理；同时要处理工具失败、超时、参数错误等异常。

## 6. Agent（智能体）

### 是什么
- 一个**能自主规划、调用工具、记忆、并循环执行直到完成任务**的 AI 系统。
- 对比普通对话：普通 LLM 是"问答"，Agent 是"做事"——主动拆解任务、调用工具、观察结果、调整策略。

### 核心组件
- **大脑（LLM）**：决策与推理。
- **规划（Planning）**：把大任务拆成子任务（如 ReAct、Plan-and-Execute）。
- **工具（Tools）**：行动手段。
- **记忆（Memory）**：短期（对话上下文）+ 长期（外部存储）。
- **反馈循环**：观察工具结果 → 调整 → 继续。

### 常见架构/模式
- **ReAct**：Reasoning + Acting，边思考边行动，交替进行。
- **Plan-and-Execute**：先规划完整步骤，再逐步执行。
- **Multi-Agent（多智能体）**：多个角色分工协作（如主控 + 专家子代理），需要协调、任务分派、结果汇总。
- **Reflexion / Self-Refine**：自我反思迭代改进。

### 关键挑战（面试高频）
- **多轮工具调用**：上下文不断增长 → 需压缩。
- **错误恢复**：工具失败、结果异常时如何兜底重试。
- **安全与权限**：越权调用工具、被 prompt 注入。
- **成本与延迟**：每轮都调用模型，很贵很慢。
- **可靠性**：长链路中任何一环出错都可能导致失败，需要校验与容错。

### 常见问题
- Q：Agent 和 LLM 的区别？
  A：LLM 是被调用的模型，Agent 是使用 LLM + 工具 + 记忆组成的自主系统。
- Q：什么时候用 Agent，什么时候直接用 LLM？
  A：任务简单直接时用 LLM 更便宜可靠；需要多步推理、访问外部系统、环境反馈时才值得用 Agent。
- Q：如何控制 Agent 不失控？
  A：设定明确的系统边界、白名单工具、权限最小化、步骤上限、人工确认关键动作、结果校验。

## 7. Skill（技能）

### 是什么
- 将**某一类任务的方法论 + 工具 + 提示词 + 执行脚本**封装成可复用的"能力模块"，供 Agent 在需要时加载使用。
- 可以理解为 Agent 的"专业工具箱/专家身份包"：遇到对应任务，自动匹配并加载该技能，按技能内部定义的标准流程执行。

### 典型结构（以本系统 Skill 为例）
- `SKILL.md`：技能说明、触发条件、执行步骤。
- 资产/脚本：参考文档、模板、可执行脚本。
- 触发机制：通过描述匹配任务 → 读取 SKILL.md → 按流程执行。

### 和 Prompt 的区别
- Prompt 是一次性的自然语言指令；Skill 是**封装成标准流程、可复用、带资产**的能力包，比 Prompt 更结构化、更稳定、更专业。

### 为什么需要 Skill
- **复用与标准化**：同一类任务不用每次从零写 prompt。
- **降低门槛**：把专家流程固化，普通用户也能完成专业任务。
- **Agent 生态**：让 Agent 具备"即插即用"的细分领域能力。

### 常见问题
- Q：Skill 和 Tool 的区别？
  A：Tool 是单个可调用的函数/API；Skill 是"方法论 + 多个工具 + 提示词"的组合能力包，更宏观、更面向任务。
- Q：如何设计一个好 Skill？
  A：职责单一、触发条件清晰、流程可执行、有校验步骤、输出标准化。

## 8. MCP（Model Context Protocol，模型上下文协议）

### 是什么
- Anthropic 于 2024 年底提出的**开放协议**，用于统一"模型 ↔ 工具/数据源"之间的连接标准。
- 目标是解决"每个模型对接每个工具都要写一遍适配器"的碎片化问题：只要工具实现一次 MCP 服务端，任何支持 MCP 的客户端/模型都能复用。

### 核心角色
- **MCP Host（宿主/客户端）**：运行模型的应用（如 Claude Desktop、豆包、IDE 插件）。
- **MCP Server（服务端）**：暴露工具/数据源/提示词的一方，实现统一接口。
- **Client（客户端）**：Host 与 Server 之间的连接层。

### 提供的三大能力
1. **Tools**：工具调用（模型可调用的函数）。
2. **Resources**：资源读取（文件、数据库、网页等数据）。
3. **Prompts**：预定义提示词模板。

### 传输/连接方式
- stdio（本地进程间）
- HTTP/SSE（远程服务）
- 认证、权限、结构化 JSON 消息

### 为什么重要（面试常问）
- **标准化**：一套协议连接所有工具，生态互通，类似"USB 接口"。
- **解耦**：工具侧只维护一份 MCP 实现，应用侧免去定制适配。
- **可扩展**：动态发现工具、按需加载。

### 与 Tool / Agent / Skill 的关系
- Tool 是单个能力，MCP 是"如何把 Tool 标准化地暴露给模型"的协议。
- Agent 通过 MCP 发现并调用工具。
- Skill 可以基于 MCP 调用多个工具来实现某一类任务。

### 常见问题
- Q：MCP 和 Function Calling 的关系？
  A：Function Calling 是模型侧的能力（怎么让模型输出工具调用）；MCP 是工具侧的标准化协议（怎么把工具注册、描述、暴露给模型）。二者是互补关系，MCP 让"定义和调用工具"更统一。
- Q：MCP 解决的核心痛点？
  A：工具接入的碎片化、重复开发、生态不互通。

## 9. 各概念之间的关系（一句话串联）

> 一句话：**LLM 是大脑，Token 是它消化和产生的字节，Context 是它当前能"看见"的工作记忆，Prompt 是喂给它的话，Tool 是它能动用的手，Agent 是用大脑+手+记忆自主做事的系统，Skill 是把某类事的成熟做法打包成可复用的专业能力，MCP 是让这些手(工具)能标准化地插到大脑上的统一接口。**

| 概念 | 一句话 | 类比 |
|------|--------|------|
| LLM 大模型 | 基于 Transformer 预测下一个 token 的语言模型 | 大脑 |
| Token | 文本处理与计费的最小单位 | 字节/词汇 |
| Context | 模型单次可见的全部信息（窗口） | 短期工作记忆 |
| Prompt | 引导模型输出的输入指令 | 你说的话 |
| Tool | 模型可调用的外部函数/API | 手/工具 |
| Agent | 能规划+调工具+记忆+循环的自主系统 | 一个干活的员工 |
| Skill | 把某类任务的方法论+工具+提示词封装成可复用能力 | 员工的专业岗位手册 |
| MCP | 模型与工具/数据源之间的统一连接协议 | USB 接口标准 |

## 10. 高频追问与易错点

### 易错点（面试别踩坑）
1. **以为模型有记忆** → 记忆是外部做的，不是模型自带。
2. **把 Token 当字符** → 中文 1 字≈1~2 token。
3. **以为上下文越长越好** → 成本、延迟、长文本质量都要权衡。
4. **把 Agent 当成单个模型** → Agent 是"模型+工具+记忆+循环"的系统。
5. **混淆 Tool / Skill / MCP**：
   - Tool = 单个可调用函数；
   - Skill = 方法论+多工具+提示词的能力包；
   - MCP = 连接"模型↔工具"的标准化协议。
6. **忽视 Prompt 注入与权限安全** → Agent 场景尤其重要。

### 高频追问示例
- 如何控制 Agent 的成本和延迟？（控制 token、步骤上限、缓存、并行）
- 上下文溢出怎么办？（摘要压缩、滑动窗口、RAG 检索、丢弃低价值历史）
- 工具调用失败了怎么兜底？（重试、降级、错误回传给模型再决策）
- 怎么减少幻觉？（RAG 检索、引用来源、降低温度、约束输出格式）
- 什么场景用 RAG 而不是微调？（实时/私有知识用 RAG；风格/固定格式用微调）
- 多个 Agent 如何协作？（任务分派、结果聚合、状态共享、避免死循环）
